Times are the actual `startedAt` from n8n's execution records; execution ids and GitHub run ids are real.

| # | Step | Result | Notes |
|---|---|---|---|
| 1 | Pre-build doc checks (shopify.dev, GitHub docs, Airtable pricing) | Pass | Confirmed all load-bearing assumptions: `orderCreate` input types and `inventoryBehaviour` enum values, `productVariants` search syntax and `inventoryQuantity`/`inventoryItem.tracked` fields, `orders` search syntax and `UPDATED_AT` sort key, GitHub's fine-grained-token permission table (Actions: write alone suffices for workflow dispatch), and Airtable's free-plan API access surviving the trial. | 3 | First test order (`#1001`, 2x `YIRGACHE-250g-WH`), next tick (exec 48) | Fail (expected/transient) | `Any SKUs?` still took the false branch — Shopify's order search index had not yet caught up to the just-created order. | 4 | Following tick (exec 49) | Fail (real bug found) | Order was found this time: `Plan updates` correctly computed `YIRGACHE-250g-WH` 15 -> 13. `Airtable update` failed: `Your request is invalid or could not be processed by the service`. Cause: the node used `POST`, but Airtable's batch endpoint treats a `POST` carrying record ids as an invalid create request; updating existing records needs `PATCH`. Fixed in `tools/build_exports.py`, a regression test added (`test_airtable_update_uses_patch_not_post`), export rebuilt, full suite re-run clean, committed (`de05a7a`). Cursor correctly did not advance on this failed run. |
| 5 | Re-imported workflow, second order (`#1002`, 1x same SKU), next tick (exec 51) | Fail (real bug found, different node) | `Airtable update` now succeeded (`PATCH`, `Stock: 12`, matching 15-3 for both orders). `Dispatch refresh` failed: `Authorization failed - please check your credentials`. Cause: my own (not-repo) import script matched a node's credential by *type* only; since `Airtable token` and `GitHub Actions token` are both `httpHeaderAuth`, it assigned the Airtable credential to the GitHub node too. Fixed the import script to match by the credential *name* the generator already embeds, not just its type. |
| 6 | Re-imported again, third order (`#1003`, 1x same SKU), next tick (exec 53) | Pass | Full chain ran clean: `Airtable update` -> `Stock: 11` (matching Shopify's 15-4), `Dispatch refresh` succeeded, `Advance cursor` -> `{"cursor":"2026-09-20T15:43:11.000Z","orders":3}`. Confirmed independently with `gh run list -R Ainz47/Projects`: a real `refresh-catalog` run, `workflow_dispatch`, started `2026-09-20T15:45:39Z` — matching exec 53 exactly — followed by a `pages-build-deployment` run, both `completed`/`success`. |
| 7 | Idempotency: two more ticks, no new orders (exec 54, 55) | Pass | Both `success`. Both still found the 3 orders in the 10-minute overlap window (`hasSkus: true`) but correctly took `Any updates?`'s false branch, straight to `Advance cursor` — no `Airtable update`, no `Dispatch refresh`. Confirmed via `gh run list`: no additional `refresh-catalog` run appeared. |
