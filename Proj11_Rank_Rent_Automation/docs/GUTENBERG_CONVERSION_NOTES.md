# Gutenberg block conversion — debug log & gotchas

Working notes from converting `templates/*.py` from one big `wp:html` blob
(v1) to native Gutenberg blocks (v2), so the same mistakes aren't repeated on
the next template. Each entry: what broke, how it was diagnosed, the fix.

## How to diagnose "Block contains unexpected or invalid content"

This is Gutenberg's block validator telling you the HTML you hand-wrote
doesn't match what core's own `save()` function would have produced from the
attributes you declared in the `<!-- wp:blockname {...} -->` comment. It
shows an "Attempt Recovery" button in the editor — but **don't just click
recovery and move on**; the root cause is always a real, fixable mismatch
between the JSON attributes and the HTML, and it'll recur on every page this
template generates if left unfixed.

**The fastest way to find the exact mismatch:** open the page in `wp-admin`
post editor, then read the browser console:

```js
mcp__playwright__browser_console_messages({ level: "warning" })
```

Look for:
```
[ERROR] Block validation failed for `%s` (%o).
Content generated by `save` function:
<the HTML core expected>
Content retrieved from post body:
<the HTML you actually wrote>
```

This is a byte-level diff of expected vs. actual — it tells you exactly
what's wrong (missing class, wrong attribute, wrong element order) instead of
guessing.

## Fix #1 — Title-visibility meta key was wrong, never worked

**Symptom:** Wanted to hide Astra's page-title banner via post meta. Used
`ast_banner_title_visibility: "hidden"` (copied from an early guess, never
verified). It silently did nothing — Astra never reads that key.

**How it was found:** Manually clicked the "Disable Title" eye icon next to
the title field in the block editor, watched `wp.data.select('core/editor'
).getEditedPostAttribute('meta')` in the browser console before/after.

**Real key:** `site-post-title` (hyphenated, no `ast` prefix at all) with
value `"disabled"`.

```php
'meta_input' => array(
    'site-post-title'            => 'disabled',
    '_astra-site-sidebar-layout' => 'no-sidebar',
),
```

This is now baked into `rr-wp-abilities`'s `rr/create-page` ability
automatically (no need to pass it manually), and into every `build_*_payload()`
function across both v1 and v2 templates.

**Lesson:** Don't trust a meta key name just because it "sounds right" or
matches a pattern seen elsewhere. If a theme setting doesn't visibly change
anything, verify the *actual* key by toggling the real UI control and reading
the data store, not by guessing at naming conventions.

## Fix #2 — `wp:cover` declared attributes it didn't actually use

**Symptom:** Hero block (`wp:cover`) flagged invalid.

**Diff:** JSON declared `"minHeight":1` and
`"style":{"spacing":{"padding":{...}}}}`, but the actual `<div>` had no
matching inline `min-height` or `padding` styles (padding had been moved to
the inner `wp:columns` instead).

**Fix:** Don't declare attributes you're not actually using in the HTML.
Removed both from the JSON comment — kept only `url`, `dimRatio`,
`overlayColor`, `isUserOverlayColor`, `align`.

**Lesson:** Every key in the block's JSON attributes must have a
corresponding, exactly-matching expression in the saved HTML. If you're not
applying a style inline, don't declare it.

## Fix #3 — Custom hex colors must go in `style.color.*`, never in `backgroundColor`/`textColor`

**Symptom:** Dark-themed `wp:media-text` sections (every other section,
alternating) flagged invalid.

**Diff:** Used `"backgroundColor":"#1a1a1a"` (a raw hex value) in the
top-level `backgroundColor` attribute slot. That slot is for a **theme
palette slug** (e.g. `"backgroundColor":"luminous-vivid-amber"` →
generates class `has-luminous-vivid-amber-background-color`). Putting a raw
hex there breaks the class-generation logic core expects.

**Fix:** Custom/arbitrary hex colors always go nested under
`style.color.background` / `style.color.text`, with **only** the generic
marker classes `has-background` / `has-text-color` (no color-named class):

```
✅ "style":{"color":{"background":"#1a1a1a","text":"#ffffff"}}
   class="... has-text-color has-background" style="color:#ffffff;background-color:#1a1a1a"

❌ "backgroundColor":"#1a1a1a"
   (raw hex in a slug-typed attribute — always invalid)
```

**Further wrinkle:** even with the nested `style.color.background` fix,
`wp:media-text` *specifically* still failed validation (its color-support
save path doesn't round-trip the same way Group/Button do). The pragmatic
fix used here: don't put a custom background directly on `wp:media-text` at
all. Wrap it in a plain `wp:group` that carries the background instead (the
exact same background pattern already proven valid on `wp:group`, e.g. the
bottom CTA section):

```
<!-- wp:group {"style":{"color":{"background":"#1a1a1a"}},"layout":{"type":"constrained"}} -->
<div class="wp-block-group has-background" style="background-color:#1a1a1a">
<!-- wp:media-text {...no color attrs...} -->
...
<!-- /wp:media-text -->
</div>
<!-- /wp:group -->
```

The Media & Text block's own text color (heading/paragraph) is still set
individually per inner block — that part validates fine.

## Fix #4 — `wp:media-text` always emits `<figure>` before content, regardless of `mediaPosition`

**Symptom:** Sections with `mediaPosition: "left"` flagged invalid; sections
with `mediaPosition: "right"` were fine.

**Diff (from console):**
```
Content generated by `save` function:
<div class="wp-block-media-text is-stacked-on-mobile alignwide">
  <figure class="wp-block-media-text__media">...</figure>
  <div class="wp-block-media-text__content"></div>
</div>
```

The figure is **always first in the DOM** — "media on the right" is achieved
purely via the `has-media-on-the-right` CSS class (flexbox order), not by
physically reordering the figure/content divs in HTML.

**The bug:** the template was conditionally swapping DOM order —
`figure + content` for `"right"`, `content + figure` for `"left"` — which is
backwards. Only the `"right"` case happened to match core's expectation by
coincidence (figure-first is the default either way).

**Fix:** always emit `figure + content_div`, never conditionally swap. Let
the `has-media-on-the-right` class (added only when `mediaPosition ===
"right"`) handle the visual side via CSS.

```python
# ❌ wrong
inner = (figure + content_div) if media_position == "right" else (content_div + figure)

# ✅ correct
inner = figure + content_div  # always — position is CSS-only, not DOM order
```

## Fix #5 — `wp:cover`'s `dimRatio` must be a multiple of 10

**Symptom:** Hero on `services_hub.py` flagged invalid — only this one, after
Fix #2 had already been applied (so it wasn't the same bug recurring).

**Diff:** declared `"dimRatio":62`; core's `save()` re-generated class
`has-background-dim-60`, not `-62`, while my hand-written HTML used `-62`.

**Cause:** Cover's dim-ratio → className conversion rounds to the nearest
multiple of 10 (`has-background-dim-{10,20,...100}`). Declaring a non-decade
value (62) doesn't break anything in the editor UI (which also snaps to
multiples of 10 on its slider), but hand-authoring an exact value produces a
className the real save function would never generate.

**Fix:** always use a multiple of 10 for `dimRatio` (e.g. `60`, not `62`).

## Fix #6 — Button block needs `has-custom-font-size` whenever a custom typography.fontSize is set

**Symptom:** Outline "Learn More" buttons (custom 13px font size) flagged
invalid even though color attributes were already correct.

**Diff:** core's `save()` included class `has-custom-font-size` on the
`<a class="wp-block-button__link ...">` element; mine omitted it.

**Fix:** any time `style.typography.fontSize` is set with a raw px/rem value
(not a preset slug), add the `has-custom-font-size` class alongside the
inline `font-size` style — for Button, Paragraph, and Heading blocks alike.

## Fix #7 — HTML entities vs. literal Unicode characters are not interchangeable for validation

**Symptom:** Same button block above also showed a content mismatch even
after the class fix — text was `Learn More →` (expected) vs.
`Learn More &#8594;` (mine).

**Cause:** they render identically in a browser, but as raw stored strings
they're different bytes. The validator does a literal string comparison of
inner content, not a rendered-DOM comparison.

**Fix:** use the literal Unicode character (e.g. `→`) directly in the PHP/
Python source, not its HTML entity equivalent. Make sure the file is saved
as UTF-8 (it will be, by default, for both languages here).

## Fix #8 — Theme CSS can win even when the block itself is perfectly valid

Not a validation bug — `is-style-outline` buttons rendered with the
**theme's** default link/border color (a blue) instead of inheriting the
button's own text color via `currentColor`, because Astra's own button CSS
has higher specificity than core's implicit border-color-inherits-text-color
behavior.

**Fix:** don't rely on implicit `currentColor` inheritance for borders.
Explicitly declare `style.border.color` (matching the text color) — same
nested-style pattern as `style.color.background`/`text` from Fix #3:

```
"style":{"color":{"text":"#ff5e14"},"border":{"color":"#ff5e14","width":"2px"}}
class="has-text-color has-border-color ..." style="border-color:#ff5e14;border-width:2px;color:#ff5e14;..."
```

This is a reminder that **zero console errors only proves the block is
structurally valid** — it doesn't guarantee the theme's CSS won't visually
override something. Always also check computed styles (`getComputedStyle`)
on the actual rendered page, not just the validator.

## Fix #9 — `wp:details`'s `<summary>` doesn't accept inline styles from JSON attributes

**Symptom:** FAQ accordion (`wp:details`) blocks all flagged invalid.

**Diff:** core's `save()` output `<summary>How do you...?</summary>` with
**no** style attribute at all; mine had
`<summary style="font-size:18px;font-weight:700;color:#1a1a1a">`.

**Cause:** `wp:details`'s typography/color block supports apply to the
`<details>` wrapper element only — there's no way to declare per-summary
styling through the block's JSON attributes, so anything written inline on
`<summary>` can never be derived from any attribute and will always mismatch.

**Fix:** style the summary element via the page's reset-CSS `<style>` block
(plain CSS selector `.wp-block-details summary{...}`) instead of inline —
exactly the same as how all the *other* technical/structural styling in
these templates is handled. The `<details>` wrapper itself *does* support
border/spacing styles via `style.border`/`style.spacing` normally (confirmed
working here with a `border.bottom` partial border, same as the `border.top`
partial border already proven in Fix #8's sibling pattern) — only the nested
`<summary>` is the exception.

## Fix #10 — Block-level elements with `has-background` get core's default padding, breaking fixed-size circular badges

**Symptom:** A "step number" badge (`<p>` styled as a 52×52 circle —
`background-color`, `border-radius:50%`, explicit `width`/`height`) rendered
as a 95×52 pill instead of a circle.

**Cause:** core's common block styles add default padding to any element
with the `has-background` class (so background-colored text blocks don't
touch their own edges). That default padding adds to the explicit width,
breaking the circle.

**Fix:** explicitly declare zero padding — both in the JSON attributes
(`"spacing":{"padding":{"top":"0","right":"0","bottom":"0","left":"0"}}`) and
the matching inline `padding-*:0` styles. Don't reach for unsupported
properties like `display:flex` to "fix" sizing issues — there's almost
always a real `spacing`/`border`/`typography` attribute that does the job
without breaking validation (see Fix #2's rule: never add inline style that
isn't derivable from a declared attribute).

## Fix #11 — Hiding theme chrome (e.g. Astra's footer credit) from page content, not a separate plugin

**Symptom:** Astra's "Powered by Astra" footer text remained visible on
every page despite an `!important` CSS rule meant to hide it.

**Cause/lesson:** when the hiding CSS is injected via `wp_head` (a plugin
hook), it lands in `<head>`, *before* Astra's own enqueued stylesheet in the
final HTML. If Astra's own rule for the same selector is *also*
`!important` (common for theme display-toggle rules), the **later** rule in
source order wins a tie — and Astra's loads after `wp_head`.

**Fix:** put the hiding CSS in the page's own `wp:html` reset-CSS block
(the same one every template already ships) instead of a separate plugin
hook. Since that block renders inside `<body>` — *after* all of Astra's
`<head>` stylesheets in source order — it reliably wins the tie. Add a
`body` ancestor to the selector too (`body .ast-footer-copyright` instead of
`.ast-footer-copyright`) as a small specificity margin of safety. This also
means the fix travels with each template automatically — no separate
plugin/Customizer-CSS step needed when deploying to a new site.

## Gotcha — TasteWP plugin re-upload/delete unreliability

Not a code bug, but cost real time during testing: on this TasteWP instance,
re-uploading a plugin zip to an **existing** plugin folder name sometimes
silently installs into a *nested* duplicate path
(`plugins/foo/foo/foo.php` instead of `plugins/foo/foo.php`) instead of
cleanly overwriting — and the **Installed Plugins list page itself serves
stale cached HTML** after delete/activate actions, making it look like
nothing happened even when it did.

**How to actually verify plugin state on this kind of host:** don't trust
`plugins.php`'s rendered list. Instead:
- Hit `plugin-editor.php` and read the `<select name="plugin">` options — OR
- Attempt to `?action=activate` the exact plugin path and read the response:
  `"Plugin file does not exist."` is an authoritative, live, non-cached
  signal that a given path is really gone.
- If a destination folder is stuck in a confusing half-state, the fastest
  fix is renaming the plugin's folder/file (e.g. `rr-wp-abilities` →
  `rr-wp-abilities2`) to sidestep the conflict entirely, rather than fighting
  the delete flow further.
- Also build plugin zips with Python's `zipfile` module (forward-slash paths
  always) rather than PowerShell's `Compress-Archive` — a rapid
  `rm` + re-`Compress-Archive` in the same command was observed to
  occasionally produce a zip that WordPress's installer extracted with an
  extra nested folder level, even though `ZipFile.OpenRead` showed a
  correctly single-level entry list immediately after creation.

## Fix #12 — Astra footer copyright: wrong setting key + Customizer drafts that never publish

**Symptom:** Wanted to replace Astra's "Powered by Astra" footer credit with a
real `© [year] {business}. All Rights Reserved.` notice (instead of hiding
the whole footer bar). `wp_client.py` already had a working-looking
`set_additional_css()` using the Customizer `customize_save` AJAX action —
modeled a new `set_footer_copyright()` after it, but it silently did nothing.

**Two separate bugs found:**

1. **Wrong setting ID.** Astra does *not* register `footer-copyright-editor`
   as its own top-level theme_mod — it's nested inside one combined
   `astra-settings` array option. The real Customizer setting ID (confirmed
   by enumerating `wp.customize.each()` in the browser console) is the
   literal bracket-notation string `astra-settings[footer-copyright-editor]`.
   That full string — brackets included — is the JSON key to send in the
   `customized` payload, not a nested object.

2. **Drafts never reach the live site.** `customize_save` without an
   explicit `customize_changeset_uuid` + `customize_changeset_status:
   "publish"` saves to an **auto-draft changeset** — the AJAX response even
   says so (`"changeset_status":"auto-draft"`) — and the live site is
   completely unaffected. This silent half-success is easy to miss if you
   only check the AJAX response's `"success":true` and not the
   `changeset_status` field. The existing `set_additional_css()` had this
   exact same bug and may never have actually published anything in
   production — it's been fixed alongside this one.

**Fix:**
```python
payload = {
    "action": "customize_save",
    "nonce": nonce,
    "wp_customize": "on",
    "theme": theme_slug,
    "customize_changeset_uuid": changeset_uuid,      # reuse existing or uuid4()
    "customize_changeset_status": "publish",          # <- without this it's a draft
    "customized": json.dumps({
        "astra-settings[footer-copyright-editor]": text,  # <- exact bracket string
    }),
}
```

**How to find a theme's real setting ID when it's not obvious:** open
`/wp-admin/customize.php`, then in the browser console run
`wp.customize.each((s, id) => console.log(id))` and filter for keywords —
faster and more reliable than guessing from the rendered field's label.

Astra supports dynamic tags inside this text field, e.g. `[current_year]`
resolves automatically — confirmed live ("© 2026 ..." appeared correctly
without hardcoding the year).

## Fix #13 — Astra has *multiple* footer-row background settings; only one matches the visible copyright bar

**Symptom:** Set `astra-settings[footer-bg-obj-responsive]` to a dark color
expecting it to color the bar containing the copyright text. Result: a
separate dark bar appeared, but the copyright text stayed in its own
unstyled **white** row right below it — two stacked bars instead of one.

**Cause:** Astra's Footer Builder has multiple independent rows (above
footer, primary footer, below footer/copyright), each with its **own**
background setting. `footer-bg-obj-responsive` is a real, valid setting —
it's just not the one wired to the row the copyright text actually renders
in. That row's real DOM class is `.site-below-footer-wrap`, and its
background setting is the `hbb-` prefixed one:
`astra-settings[hbb-footer-bg-obj-responsive]`.

**How it was actually confirmed (don't just guess the prefix):**
```js
document.querySelector('footer.site-footer').children  // find which element
// wraps the copyright text and note its className, e.g. site-below-footer-wrap
```
then set one candidate setting at a time and re-check
`getComputedStyle(thatElement).backgroundColor` on the live page — don't
trust that "success":true in the AJAX response means it touched the right
element, only that the setting ID itself was valid and saved.

**Fix:** use `astra-settings[hbb-footer-bg-obj-responsive]` for the
copyright row's background, not the more generically-named
`footer-bg-obj-responsive`. Reset the wrong one back to an empty background
object (don't leave it set) so there's no second stray colored bar.

## General checklist for new native-block templates

Before considering a new block "done," open it in the post editor and check
for **zero** console errors (not just zero visible "Attempt recovery"
banners — always check the console, some validation failures are silent in
the UI until you scroll to that exact block):

1. Every attribute declared in the `<!-- wp:x {...} -->` comment has a
   byte-for-byte matching expression in the saved HTML (style attribute,
   class name, or both).
2. Custom hex colors → always `style.color.{background,text}`, never the
   top-level `backgroundColor`/`textColor` slug attributes.
3. Don't assume DOM element order follows the visual/positional attribute —
   check core's actual `save()` output (via the console diff) for blocks with
   a "position" or "alignment" concept (`media-text`, `columns`, etc).
4. If a block's color/background support doesn't round-trip cleanly, wrapping
   it in a plain `wp:group` with the background instead is a reliable
   fallback — `wp:group`'s color support is simple and has validated cleanly
   every time in this project.
